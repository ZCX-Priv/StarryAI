# 输入操作栏溢出收纳设计

## 背景

聊天输入区底部的操作栏当前采用单行展示，包含附件按钮、模式选择按钮、若干功能按钮、更多菜单按钮，以及发送或停止按钮。随着窗口变窄、侧边栏展开或功能按钮数量增长，这一行存在横向溢出风险，尤其会影响发送按钮的可见性和可点击性。

本次改动目标是在不改变现有交互心智的前提下，为操作栏增加动态收纳策略，使默认展示的功能按钮在空间不足时逐个进入更多菜单，同时确保关键操作始终可见。

## 目标

- 防止 `input-actions` 横向溢出。
- 保证 `attachBtn` 和 `quickBtn` 始终留在主栏。
- 保证发送按钮或停止按钮始终位于消息发送框内，不被裁切、不换行、不被挤出。
- 让普通功能按钮随着宽度变窄按顺序逐个进入更多菜单。
- 当宽度恢复时，让被收纳的按钮按原顺序回到主栏。
- 保持主栏按钮和更多菜单中的点击行为一致。

## 非目标

- 不改动附件按钮本身的功能实现。
- 不改动模式选择菜单的内容和交互。
- 不引入新的功能按钮样式体系。
- 不改变 `banner.json` 中功能项的配置格式。

## 约束

- `attachBtn` 和 `quickBtn` 不参与折叠。
- 发送态下显示 `stop-btn`，非发送态下显示 `send-btn`；两者都属于右侧固定保留区。
- 功能按钮的折叠顺序遵循当前展示顺序的末尾优先，即从右往左逐个收纳。
- 当前已激活的功能按钮即使原本应被折叠，也需要继续保留在主栏，便于用户感知当前模式并快速退出。
- `moreBtn` 仅在确实存在被收纳的功能按钮时显示。

## 方案概览

操作栏按职责拆为三个区域：

1. 左侧固定区：`attachBtn`、分隔线、`quickBtn`
2. 中间弹性区：普通功能按钮与 `moreBtn`
3. 右侧固定区：弹性占位、`send-btn` 或 `stop-btn`

布局核心原则如下：

- 左右固定区不可被压缩。
- 中间弹性区根据剩余宽度决定可展示的普通功能按钮数量。
- 当普通功能按钮放不下时，从末尾开始移入更多菜单。
- 当空间恢复时，从更多菜单中按原顺序移回主栏。

## 数据与渲染模型

现有 `bannerActions` 保持不变，但渲染时拆分为以下集合：

- `pinnedActions`：当前固定保留的按钮，仅包含 `attachBtn`、`quickBtn`
- `candidateBannerActions`：可参与折叠的功能按钮，来自 `bannerActions`
- `activePinnedBannerAction`：当前激活且需要强制留在主栏的功能按钮，最多一个
- `inlineBannerActions`：本轮计算后仍留在主栏的功能按钮
- `overflowBannerActions`：需要显示在更多菜单中的功能按钮

最终展示规则如下：

- 主栏始终渲染 `attachBtn`、分隔线、`quickBtn`
- 主栏按顺序渲染 `inlineBannerActions`
- 当 `overflowBannerActions.length > 0` 时渲染 `moreBtn`
- 右侧始终渲染 `send-btn` 或 `stop-btn`

## 宽度计算策略

通过 `ResizeObserver` 监听操作栏容器尺寸变化，并在以下时机重新计算可见按钮：

- 操作栏宽度变化
- 窗口尺寸变化
- 发送状态切换，导致 `send-btn` 和 `stop-btn` 显示变化
- 当前功能模式变化，导致某个功能按钮需要强制留在主栏
- 功能配置加载完成或数量变化

计算步骤：

1. 获取操作栏总宽度。
2. 测量左侧固定区宽度。
3. 测量右侧固定区宽度，并附加安全间距，确保发送按钮不会贴边或被覆盖。
4. 计算中间弹性区的可用宽度。
5. 按候选功能按钮的原始顺序累计宽度，确定最多可显示几个。
6. 若存在激活中的功能按钮，优先为其预留宽度；其余按钮再按顺序填充。
7. 将未能容纳的功能按钮放入 `overflowBannerActions`。

## 按钮收纳顺序

默认功能按钮按当前展示顺序排列，例如：

`图像生成 -> 解题答疑 -> 翻译 -> 编程 -> 深入研究 -> 数据分析`

当空间不足时，折叠顺序为：

`数据分析 -> 深入研究 -> 编程 -> 翻译 -> 解题答疑 -> 图像生成`

即从右往左逐个进入更多菜单。

如果当前激活的是某个普通功能按钮，例如 `编程`，则在空间不足时：

- `编程` 仍留在主栏
- 其右侧按钮优先进入更多菜单
- 如仍不足，再继续折叠其他未激活按钮

## DOM 与测量策略

为避免依赖估算宽度，使用真实 DOM 宽度进行测量。

建议增加以下引用：

- 操作栏根节点 `actionsRef`
- 左侧固定区 `leadingRef`
- 右侧发送区 `trailingRef`
- `moreBtn` 宽度测量引用
- 每个普通功能按钮的宽度引用表

测量要求：

- 使用 `offsetWidth` 或 `getBoundingClientRect().width`
- 计入按钮间距和菜单按钮本身宽度
- 当存在溢出项时，计算中需预留 `moreBtn` 的宽度

## 样式策略

需要补充以下布局约束：

- `input-actions` 保持单行布局，不换行。
- 左右固定区设置 `flex-shrink: 0`。
- `send-btn` 与 `stop-btn` 设置 `flex-shrink: 0`，禁止被压缩。
- 中间弹性区设置 `min-width: 0`，允许根据剩余空间收缩。
- 必要时轻微收紧普通按钮的横向内边距，但不改变主要视觉层级。

样式目标不是让按钮硬挤在一行，而是通过收纳机制避免硬挤。

## 交互与行为

- 点击主栏中的功能按钮，行为与当前一致。
- 点击更多菜单中的功能按钮，行为与主栏一致，并在触发后关闭菜单。
- 当前激活功能按钮若留在主栏，视觉选中态保持不变。
- 当前无溢出项时，不展示更多菜单按钮。
- 当进入发送中状态，若 `send-btn` 被 `stop-btn` 替换，应重新计算可用宽度。

## 错误处理与降级

- 当 `ResizeObserver` 不可用时，降级为监听 `window.resize`。
- 当某个按钮宽度尚未测量到时，延后到下一帧重算，避免出现错误折叠。
- 在极窄宽度下，允许所有普通功能按钮全部进入更多菜单，但不允许 `attachBtn`、`quickBtn`、`send-btn`/`stop-btn` 消失。

## 测试与验收

手动验收至少覆盖以下场景：

- 默认宽度下，所有应展示的按钮正常显示。
- 缩窄窗口时，普通功能按钮按从右往左顺序逐个进入更多菜单。
- `attachBtn` 和 `quickBtn` 在任何宽度下都保持可见。
- `send-btn` 在任何宽度下都保持位于输入框内。
- 发送中切换为 `stop-btn` 后，布局仍不溢出。
- 当前激活的普通功能按钮在窄宽度下仍保持在主栏。
- 窗口重新变宽后，按钮按原顺序回到主栏。
- 从更多菜单点击任一功能按钮，行为与主栏按钮一致。

## 实施摘要

本次改动将在现有更多菜单基础上增加一层动态分配逻辑，不改变功能配置源，只改变主栏与更多菜单之间的分流策略。核心收益是消除输入操作栏的横向溢出风险，并把发送按钮的可见性提升为布局层面的硬约束。
